# latency-test

一个**纯标准库、零依赖**的链路探针：在浏览器里点一下，测出「你的机器 → 服务器」这条真实链路的延迟、抖动、上下行速率，以及**流式数据到达节奏**。

专门用来区分两类长得一模一样的卡顿：

- 服务器/出口真的慢
- 链路把下行压住了（或中间代理在缓冲流式响应）

## 为什么需要它

排查「页面/接口很慢」时，只看总耗时无法判断瓶颈在哪。这个探针把链路拆成五个可独立测量的量，任何一项异常都能直接指向具体环节：

| 测量项 | 说明 | 异常时的含义 |
|---|---|---|
| 复用连接 RTT | 同一 TCP 连接上连续 15 次请求 | 纯网络往返延迟与抖动 |
| 冷连接 RTT | 每次新建连接（含 DNS + TCP + TLS） | 建连开销；与复用 RTT 之差 = 握手成本 |
| 下行吞吐 | 下载 4MB（可选 8MB） | 接收方向带宽 |
| 上行吞吐 | 上传 2MB（可选 4MB） | 发送方向带宽 |
| 流式到达节奏 | 服务端每 20ms 稳定写 8KB，客户端记录每次读取时刻 | 成批到达/秒级空档 = 下行被缓冲或阻塞 |

**流式节奏是关键项。** 声明的 `Content-Length` 会让中间代理先把整个 body 收完再转发，从而完全掩盖卡顿；所以 `/api/stream` 强制使用 `Transfer-Encoding: chunked`，让数据必须逐块穿过链路。

## 快速开始

```bash
./start.sh          # 默认 8005，可用 LAT_PORT 覆盖
./stop.sh
```

打开 `http://<host>:8005/` 即可。页面有两个 tab：

- **测试**：逐项执行，实时显示数值与 RTT 曲线
- **汇总**：整体评价 + 诊断结论 + 速率趋势 + 指标汇总 + 历史记录（可复制/导出 JSON）

「开始测试」约 15 秒；「全部」约 40 秒（更大的传输量，结论更稳）。每次跑完自动存 `localStorage`（最多 60 条）并跳到汇总页。

## 判定规则

整体评价按以下顺序短路，先命中先返回：

| 条件 | 结论 |
|---|---|
| 下行 < 10 KB/s 且上行 > 50 KB/s 且上/下行 > 5 | **复现故障：下行被阻塞** |
| 下行 < 100 KB/s 且上/下行 > 5 | 下行偏慢且不对称 |
| 流式 > 3× 或最大空档 ≥ 3s | 流式被缓冲/阻塞 |
| RTT > 300ms / 下行 < 100 / 上行 < 100 / 流式 > 1.8× 任一 | 部分指标异常 |
| 其余 | 链路正常 |

单项分级：

- RTT：≤100ms 良好，≤300ms 偏高，>300ms 高
- 速率：≥500 KB/s 良好，≥100 偏慢，≥3 很差，<3 阻塞
- 流式：≤1.8× 且空档 <1s 正常，≤3× 有缓冲，>3× 严重阻塞，空档 ≥3s 秒级空档

> 经 CDN 时每个分片常被拖到 25~35ms，1.3~1.5× 属正常，不必当成故障。

## 怎么读结果

- **探针快、目标应用慢** → 不是本机出口带宽问题，瓶颈在该客户端连接或进程
- **探针同样慢（下行 <3 KB/s 或流式 ≫1.5×）** → 链路确实在压下行
- **上行远高于下行且下行只有几 KB/s** → 典型的不对称限速/阻塞，常见于中间设备对下行做了整形
- **流式倍数正常但空档有秒级峰值** → 间歇性阻塞，往往比稳定低速更难察觉

## API

所有端点都返回 `Cache-Control: no-store`，并带 `Access-Control-Allow-Origin: *`。

| 端点 | 说明 |
|---|---|
| `GET /` | 测试页面（单文件 HTML） |
| `GET /api/ping[?close=1]` | 返回服务端时间戳；`close=1` 让响应后关闭连接（测冷连接） |
| `GET /api/download?kb=N` | 下载 N KB（1 ~ 65536） |
| `GET /api/stream?chunks=&size=&interval=` | chunked 流式输出；`chunks` 1~20000、`size` 1024~1048576 字节、`interval` 0~5000 ms |
| `POST /api/upload` | 读掉请求体，返回 `{"received": <字节数>}` |
| `GET /api/info` | 回显 `Host` / 客户端 IP / `X-Forwarded-For` / `CF-Ray` / `CF-IPCountry` |

```bash
# 最小自检
curl -s 127.0.0.1:8005/api/ping
curl -s -o /dev/null -w '%{size_download}\n' '127.0.0.1:8005/api/download?kb=1024'
curl -s -o /dev/null -w '%{size_download}\n' '127.0.0.1:8005/api/stream?chunks=10&size=8192&interval=5'
```

## 实现要点

- **纯标准库**：`http.server.ThreadingHTTPServer` + 单文件 HTML，无 pip 依赖、无构建步骤。
- **`/api/stream` 必须 chunked**：声明长度会被代理整体缓冲，测不出卡顿。早期版本「既不声明长度也不发 chunked」会让 `curl` 永久挂起（连接不关、无结束标记），已修。
- **流式分片要小于链路吞吐上限**：默认 8KB/20ms ≈ 400 KB/s。分片速率若高于实际链路带宽，限速会天然拉长耗时，导致倍数虚高。
- **`TCP_NODELAY`**：每个请求都关掉 Nagle，避免小包被合并后干扰 RTT 与节奏测量。
- **历史存 `localStorage`**：最多 60 条，纯本地，不上传任何数据。

## 部署建议

- 放在**与业务同一条链路**的机器上才有对照意义（同一个 CDN、同一个出口）。
- 反向代理后面时不要开响应缓冲（nginx: `proxy_buffering off;`），否则流式项会失真。
- 测速会消耗真实流量：「全部」一轮约 20MB 上下行合计。
